# 评论 AI 分析系统功能梳理与优化建议

更新时间：2026-07-05

## 1. 系统定位

当前系统已经不是单一的“评论导入后做 AI 分析”工具，而是一套面向评论舆情和内容反馈的全流程平台：

- 从 Shopee、YouTube、TikTok、Facebook 等渠道采集或导入评论。
- 按商品、视频、推文/舆情三类业务场景建立分析项目。
- 对评论做情感、意图、问题、主题、证据、摘要和策略建议分析。
- 生成分析报告、评论明细、行动看板和共享报告。
- 支持工作空间、多用户、超管、配额、模型配置、爬虫配置、监听任务等后台能力。

一句话概括：系统的核心价值是把“海量评论”变成“可解释的洞察”和“可跟进的行动”。

## 2. 当前功能地图

已具备功能：

- 登录、注册、退出登录。
- 邀请码注册。
- 登录会话管理。
- 普通用户修改自己的密码。
- 用户启用、禁用。

- 超管标记或取消用户的超管身份。
- 工作空间管理。
- 多工作空间切换。
- 工作空间成员管理。
- 成员角色：owner、admin、analyst、viewer。
- 超管可以查看全部工作空间、全部用户和全部任务。

相关数据模型：

- `User`
- `AuthSession`
- `InviteCode`
- `Workspace`
- `WorkspaceMember`
- `Subscription`

## 3. 核心业务流程

### 3.1 文件导入分析流程

1. 用户新建分析项目。
2. 选择项目类型：商品、视频、推文/舆情。
3. 上传 CSV、XLS 或 XLSX。
4. API 解析文件并校验字段。
5. 系统创建 `Task`、`ImportRecord`、`Review`。
6. 用户启动 AI 分析。
7. API 创建 `AnalysisRun` 并写入队列。
8. Worker 分批调用 AI 模型。
9. 每条评论生成 `ReviewAnalysis`。
10. Worker 汇总生成 dashboard 快照。
11. 用户查看报告、评论明细、行动项。
12. 用户可分享报告或打印 PDF。

### 3.2 评论采集分析流程

1. 用户在评论采集页面输入链接。
2. 系统识别平台和分析类型。
3. API 创建 `CrawlJob`。
4. Worker 调用 Python 爬虫。
5. 爬虫返回标准评论数据。
6. 采集任务完成后可导入为分析项目。
7. 用户或系统触发 AI 分析。
8. 后续进入报告和行动闭环。

### 3.3 监听任务流程

1. 用户创建监听任务。
2. 设置链接、间隔、最大采集数量、是否自动分析。
3. 系统根据 `nextRunAt` 调度。
4. 到点后创建采集任务。
5. 采集完成后更新监听状态和最近运行结果。
6. 如果开启自动分析，则导入评论并启动 AI 分析。

### 3.4 报告分享流程

1. 用户在报告页创建分享链接。
2. 系统生成 token。
3. 外部访问 `/share/:token`。
4. API 校验链接是否启用、撤销、过期。
5. 公开页面加载报告。
6. 系统增加浏览次数。

### 3.5 行动闭环流程

1. 用户在报告中发现问题或机会。
2. 从报告或评论明细创建行动项。
3. 指定负责人、优先级、截止日期。
4. 团队按状态推进。
5. 查看关联证据评论。
6. 完成后归档，形成复盘记录。

## 4. 当前系统亮点

### 4.1 分析场景已经从电商扩展到内容和舆情

系统不仅支持商品评论，还支持视频类、推文类。不同类型有不同指标、不同提示词和不同报告表达，这是一个很关键的产品升级。

### 4.2 报告不是单纯图表，而是带证据链

报告里既有总体指标，也有观点聚类、动态标签、质量提醒、重复评论识别、证据评论。这让报告更容易解释，也方便培训和客户演示。

### 4.3 已经具备运营闭环

评论明细、纠错、每日简报、项目对比、行动看板这些功能，使系统从“分析工具”接近“运营工作台”。

### 4.4 多租户和后台能力基本成型

工作空间、成员、配额、超管、邀请码、模型配置、爬虫配置都已经有基础能力，后续商业化或内部多团队使用会比较顺。

### 4.5 异步队列架构适合长任务

AI 分析和评论采集都走队列，不会把 Web 请求堵死。对几千条、几万条评论这种长任务场景是必要设计。

### 5.1 P0/P1：采集平台能力需要前后端完全对齐

开发进度：进行中。已补充 Facebook/TikTok 链接识别、采集提示和部分后台识别逻辑；仍需把 Facebook “所有评论”强制切换、插件监听和全链路采集验收补齐。

现状：

- Python 爬虫文档已经包含 Shopee、YouTube、TikTok、Facebook。
- API 和 UI 的平台识别已扩展到 YouTube、TikTok、Facebook 等链接类型，但浏览器插件监听和各平台全链路验收仍需继续补齐。

## 7. 建议的验收清单

### 评论采集验收

- Facebook 图片帖可切换到所有评论并采集到底。
- Facebook Reel 可采集评论并保留评论 ID。
- TikTok 视频可打开评论弹窗并持续拉取 cursor。

- 采集结果可以一键导入分析。
- 监听任务可以按计划运行并自动分析。

### AI 分析验收

- 商品类报告不出现视频/推文专用表达。
- 视频类报告不出现“商品名称”等电商专用表达。
- 推文类报告有支持度、反对点、事实核查和风险视角。
- 英文评论输出英文或指定报告语言。
- 泰文评论能保留原文证据并给出可读总结。
- 失败批次能重试，局部失败不影响已完成结果。

### 报告验收

- 情感、来源、意图、问题、词云图表全部渲染。
- 打印跨页不卡断关键图表。
- 分享链接可访问、可撤销、可过期。
- 分享报告版本符合预期。
- 行动项能从报告证据创建并回到看板跟进。

### 后台验收

- 超管不限额。
- 超管可查看全部用户和任务。
- 超管可启用/禁用用户。
- 超管可重置密码为 `123456`。
- 普通用户可修改自己的密码。
- 被禁用用户无法继续登录或调用接口。
- 操作日志能查到关键后台操作。

## 8. 总结判断

当前系统的主干已经比较完整，具备“采集、导入、AI 分析、报告、明细、行动项、后台管理”的闭环能力。真正影响下一步交付质量的重点，不是再堆更多页面，而是把已有能力打通、打稳、打透。

最优先要补的是三件事：

1. 采集链路稳定性，尤其是 Facebook 和 TikTok 大体量评论。
2. 多语言和多场景分析一致性，避免商品、视频、推文三类表达混乱。
3. 平台治理能力，包括审计日志、配额周期、敏感配置安全和任务可观测性。

如果这三块补齐，系统就可以从“能演示、能试用”进一步升级为“能长期交付、能多人协作、能支撑客户项目”的产品化平台。
